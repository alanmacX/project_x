# Art direction, sourcing and irregular cards

Read this for a themed or visually ambitious canvas. The native example demonstrates valid structure; it is not a visual template. The Control Resonant example is a zero-asset structural baseline, not the ceiling of the skill.

## Start from the user's world

Identify what makes the theme recognizable beyond its name: silhouette, object/material, composition, typography, color relationship, imagery or a distinctive recurring motif. Research factual themes using primary sources before depicting characters or quoting text. Choose a coherent visual thesis and translate it into the canvas rather than reproducing a generic dashboard with theme labels.

For open-ended requests, briefly explore competing directions in your working notes, then develop the strongest. A game fan might want a collected desktop of artifacts, a cinematic subject with floating data, or an editorial cover with a restrained utility strip. These are possibilities, not required presets. Let a visual anchor earn its space; remove decorative pieces that only repeat the theme. Preserve useful information and the user's editing freedom.

Do not automatically default to six equal rounded rectangles, cream everywhere, emoji, tiny all-caps labels, repeated glass boxes or a grid because it validates easily. Cream is a useful tool palette, not a mandatory artwork palette. Asymmetry, overlapping stickers, one broad quiet area, intentional edge cropping and mixed scale can work while host border/shadow remain consistent. A deliberate grid is valid when it serves the concept. More capabilities do not necessarily make a better canvas; select those useful to this profile.

## Actively source assets

When real imagery would improve the work, search before choosing a zero-asset fallback. User-provided originals → creator/publisher media or press pages → licensed libraries/open archives → credible original fan-art sources with stated terms are useful starting points. Use image search to discover candidates, then open the actual source page. Search separately for key art, isolated subject/render, prop/weapon/object, texture or pattern; a whole screenshot is rarely the best cutout. Prefer recognizable silhouettes, coherent light direction and adequate resolution at final size. Inspect shortlisted files, not only thumbnails or search descriptions.

Example discovery for a Control Resonant fan: Remedy's official [media page](https://www.remedygames.com/media-and-influencers) links release-specific media kits, while the [game page](https://www.remedygames.com/games/control-2) supplies factual context. These are source leads, not a blanket license to redistribute or use commercially. Do not contact a rights holder, log into an unrelated account or publish a work merely to obtain material.

Download selected assets locally when the task calls for packaging them, confirm actual media type/dimensions and inspect them. Follow tool display/download restrictions; do not fetch a remote image merely to bypass a display restriction. Do not hotlink images in `.fridge`, scrape a private user's files, ship a random URL as an image, or silently use third-party assets for an app's commercial promotional release. Record source URL, creator, stated terms (or unknown), local checksum, intended role, transformations and attribution in a separate `.sources.json`. Public accessibility alone does not establish rights. If a source cannot be retrieved or used, try another suitable source or generate an original alternative; explain the actual limitation without abandoning art direction.

If image generation is available, use the imagegen skill/tool for original hero objects, illustrated cutouts, texture or a missing motif when it serves the direction. Generate assets, not the finished canvas with baked-in capabilities. Ask for transparent background when needed, controlled framing and enough breathing room around the silhouette. Preserve identity when editing a supplied image and label invented motifs as original, not official game items or real user photos. Never claim a generated image is an official render. Do not ask imagegen to paint host white border/shadow, time, battery, schedule or long editable labels into the asset. Keep those editable/native. Simple original geometric artwork can instead be authored as vector/code and rasterized locally; distinguish an intentional shape from a claimed photographic cutout.

## Make shapes from real alpha

A `subject` card can be a photographed/illustrated subject (`subjectPhoto=true`) or an original silhouette filled with a chosen material (`subjectPhoto=false`). Both require a real transparent PNG and a contour derived from that same alpha. An original ticket, torn paper, faceted shard, organic label or hand-drawn cloud can be a designed asset, rather than a guessed polygon called a person. Do not substitute a rounded rectangle or ignore holes just to pass validation.

Prepare the cutout using the app's subject tool or image editing capability. Open `previewer/subject-tool.html` to inspect a local transparent PNG and export its asset bytes, original dimensions, checksum, bounds and `cardFields`. It calls production `SubjectGeometry.traceMask`; it does not segment an opaque photo. Copy the exported asset into the package with a unique `asset://N` key and remap cardFields.cutout accordingly. This auxiliary JSON is not itself a `.fridge` package. The tool preserves original PNG bytes and shares its normalized coordinate space with outline; it cannot magically fix a bad segmentation.

Before assembly inspect alpha on light and dark backgrounds. Remove accidental transparent margins during source preparation, retain intentional thin parts and meaningful disconnected components, and keep holes transparent. If cropping/resizing/editing alpha, re-extract the outline from the resulting image; never normalize outline to a tighter box while leaving the image unchanged. For contour preparation use a working transparent PNG of at most 1024px long edge, keeping the high-resolution original, avoid oversize base64 and pathological contour detail. The helper blocks oversized working images and the current loop/point limits. The production tracer has a tiny-corner threshold that becomes unreliable on very large rasters; resize the working image and re-trace rather than fabricating missing geometry. Use bounded native contour reduction, not repeated heavy simplification that erodes character. Host handles white border, surface factor and thickness; don't duplicate them inside the asset.

## Compose with the silhouette

Use the shape to determine information placement. Locate the quiet interior, the side with useful negative space, and the edge suitable for attachment. A head/face or important prop is usually a poor place for data. Free capability placement allows a reading surface to extend beyond the subject; respect the host's allowed reading style and keep the actual content readable. Call `FridgeReadouts.inspectCard(card)` after normalization to inspect requested vs fitted placement and minimum content dimensions. You may also inspect `CanvasLayout.safeContentBox(card)`; it is a geometry aid, not a guarantee that the photograph underneath is visually quiet.

Try an integrated brush readout in a low-detail area, a hook tag at an intentional contour feature, or an inside/outside edge attachment where it strengthens the silhouette. Use cloud/bare/tag/sticker as the current host permits, badge for battery, album as its own layout. Choose a backing because of information density and contrast, not merely to demonstrate all available styles. Prefer subject-specific placement to randomly rotating every card. Groups express designed relationships, not an excuse to hide collisions.

Maintain editable separation: hero/photo/mask, native capability, decorative text and supporting shapes. One capability per card, but a photographic hero can be grouped with supporting capability cards. Decorative images should not be falsely presented as interactive or live. Only rasterize the decorative asset that cannot be native; never flatten the full composition, dynamic data or all text to one image.

## Critique the rendered work

Use the actual `.fridge` previewer at the target aspect and a small realistic display size. Spend a revision on the strongest visible defect, then render again. A legal package and issues=[] are only structural results.

Ask in working notes: is the theme recognizable without its title; does the focal image lead; do silhouettes and overlap have a reason; is there breathing room; do photos share an intentional palette/light/scale; do native surfaces integrate; does every useful readout stay legible; are edge crops intentional; does any text truncate; is it better than the zero-asset baseline? Don't turn these into a mandatory identical layout or a self-awarded numerical score. A quiet and convincing composition beats additional ornaments.

Check sparse data, long names, unknown battery and multiple time/date values. Preview both light/dark imagery for capability ink, contour at card scale, and transparency around all disconnected pieces. Preserve package/assets/sources/QA receipts. For commercial promotion, resolve asset permissions before publishing; for app/Form parity retain native evidence rather than asserting pixel identity. If a direction fails, change composition or asset choice, not just the shade of the same rectangular template.

Treat tiny display sizes separately: structural readout fit does not prove that decorative text is readable. Test at the recipient's actual widget width; reduce secondary wording, enlarge essential text or remove low-value labels before shrinking the whole composition. Record any remaining small-size limitation instead of calling every tested size visually approved.
