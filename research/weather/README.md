# 天气接入：本地 App 的可行路径

核对日期：2026-10-31。目标：作品和私人数据继续保存在本机，应用不建设天气后端。这里记录接入研究，产品包没有新增天气能力或网络轮询。

## 结论

客户端可以通过 HTTPS 取得天气；当前主要障碍是正式分发时的服务授权、共享凭据保护和桌面长期刷新政策。优先考虑一次读取未来预报并缓存时间线，在桌面本地选取对应时段。需要持续自动获取实况的方案，必须另外满足数据供应商的授权与流量条件。

## 1. 竞品公开披露了什么

| 产品 | 可核实的公开内容 | 用于我们决策的部分 |
| --- | --- | --- |
| Widgetsmith | 可读隐私页声明天气坐标发给 Apple Weather；2023 年作者笔记记录当时使用 Open Weather / Dark Sky 并评估迁移 [1,2] | 天气使用供应商；按地点请求。历史笔记不作为当前二进制的数据源清单 |
| iScreen | 2026-09-29 隐私政策说明定位用于天气，以及存在网络服务；查阅内容没有确认具体天气供应商 [3] | 能确认联网/位置参与，不能确认客户端直连、代理或缓存拓扑 |
| 亿象 | 浏览器可访问鸿蒙版帮助、安装和编辑流程；没有得到可核实的供应商和鉴权说明 [4] | 不按同名 Android 应用或论坛说法推断鸿蒙实现 |

可借鉴的结构是供应商数据、地点配置和显示样式分离。竞品天气并没有揭示一个可以直接读取华为天气 App 私人缓存的通用接口。

## 2. 四条路径的实际条件

### 华为 Weather Service Kit

本机 SDK 包含 `@kit.WeatherServiceKit`，接口是 `getWeather` / `getWeatherWithContext`，请求字段为 `location`、`limitedDatasets`。当前官方简介明确只向系统应用开放，且不支持模拟器 [5]。普通第三方的冰箱贴不能直接把此路线列为交付方案。网上有使用不存在字段的示例，未作为实现依据。

### 和风天气

支持 JWT / API KEY。其安全指南为客户端 JWT 推荐认证服务器，也列出代理方案；公开的客户端限制列举 iOS / Android，没有确认鸿蒙专用凭据校验 [6]。直接 HTTP 请求在技术上可做，正式商业分发需要处理凭据复制和额度保护，不能将私钥硬编码。

基础服务当前每月前 5 万次免费，随后 95 万次每次 0.0007 元，再后 400 万次每次 0.0005 元 [7]。假设每设备每天使用 8 小时、每小时两个请求、每月 30 天：1000 台约 48 万次，约 301 元/月；10000 台约 480 万次，约 2565 元/月。只是流量模型，实际按端点数、有效使用时长、阶梯与账单规则计算。同机多个画布共用缓存可以减少重复，跨手机同城市仍会产生独立请求。

### Open-Meteo

免费接口免密钥，但服务条款限定非商业用途；付费接口提供商业使用。数据的 CC BY 许可与托管接口的使用条件需同时满足 [8]。有付费/广告的正式产品不能直接依赖免费额度。付费凭据如何在原生客户端安全使用仍需解决。

### MET Norway

公开数据采用 NLOD / CC BY，要求来源署名；API 要有可识别 User-Agent、缓存和条件请求，并遵守 Expires。条款限制移动应用在未使用期间持续取数，整个应用超过 20 请求/秒需特别约定，高流量需缓存代理 [9,10]。因此它适合验证无密钥的前台预报下载；桌面持续后台轮询不能直接套用。数据是数值预报，不能标成气象站实时实况。

## 3. 已完成的真实请求

运行 `node research/weather/probe.cjs`，仅请求公开的上海市中心测试坐标，不读取设备定位。2026-10-31 15:16（北京时间）：

- `api.met.no` 返回 HTTP 200，38252 bytes，端到端约 1983 ms。
- 返回 87 个预报时间段，第一段 15:00 的温度为 21.7°C、天气代码 clearsky_day。
- 响应含 Expires / Last-Modified。没有使用密钥。
- 测量位置是这台 Mac 的 Node HTTPS；没有将它记为鸿蒙原生网络测试或全国连通性测试。

结果文件：本机 `output/weather-research-20261031/met-probe.json`。脚本只执行一次请求，不创建后台任务；重新执行应遵守上一响应的缓存到期时间。

## 4. 适合第一版的设计

**先交付预报型天气卡**：用户选城市 → App 前台下载未来时段 → 本机持久化缓存 → 首页和多个桌面实例根据当前时间选同一时段。只向供应商发送选定城市中心坐标，定位可选；作品、照片、课表不参与天气请求。

- 小尺寸：城市、天气图标、温度、最高/最低；完整页再看逐时预报。
- 显示更新时间，过期保留最后结果；不把旧预报显示为刚刚取得的实况。
- 同地点/供应商/数据集使用一个请求和缓存；同一时刻的请求合并，失败退避。
- 记录 `fetchedAt`、`providerUpdatedAt`、`validAt`、`expiresAt`，分清下载时间和预报有效时间。
- 缓存响应使用独立天气表/文件，不写入可编辑画布 JSON，也不触发整个作品库备份。
- 展示仅更新该数据源引用的卡片；没有新像素时不重新准备图像或整张投递。

如果要求长期不打开 App 也持续拿到新实况，需要供应商明确允许客户端后台调用，并解决端侧授权和成本。可选择申请支持鸿蒙设备凭据的合作方案；引入认证/缓存网关需要改变无自建服务的约束，当前未实施。让普通用户自行填 Key 会增加首次使用步骤，不作为默认流程。

## 5. 接入当前代码时的边界

原来的 `CardSchema` 明确退休了旧 weather / parcel 能力。新天气必须定义经过版本门禁的模型和迁移，继续清除旧网络字段；不能只把 weather 加回能力白名单，让旧参数重新生效。

实现时分开 `WeatherProvider`、本地 `WeatherSource` 和显示投影。公开作品只携带显示意图和样式，城市/坐标/授权不跟随分享，备份按私人数据规则处理。宿主能力样式继续使用当前字体、底板和 HDS 设置，不增加独立账户或天气服务菜单。
